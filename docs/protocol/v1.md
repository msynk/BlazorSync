# BlazorSync replication protocol, version 1

- **Status:** Draft. Message semantics and JSON encoding are implemented by the reference authority and
  engine and checked by fixtures. The HTTP binding (section 8) is not implemented yet (Phase 4).
- **Fixtures:** [`fixtures/valid`](fixtures/valid) must decode and re-encode to equivalent JSON;
  [`fixtures/invalid`](fixtures/invalid) must be refused. `WireFormatTests` enforces both.
- **Conformance:** `LocalStoreConformanceTests` and `AuthorityConformanceTests` in
  `src/BlazorSync.Tests/Conformance` are the executable form of sections 4–6.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119
and RFC 8174 when, and only when, they appear in all capitals.

## 1. Roles and scope

- A **replica** holds a local copy of one collection for one scope and originates writes.
- The **authority** (server) owns the current state of every document, assigns versions, decides every
  write, and serves the change feed.
- A **collection** is a set of documents of one type, identified by id. Each message in this document is
  exchanged for exactly one collection and one scope; how they are named is part of the binding
  (section 8). Scopes and authorization are specified in ADR-010 and are not yet part of this version.

## 2. Data model

### 2.1 Documents

A document is a JSON object defined by the application. It MUST contain:

| Member | Type | Meaning |
|---|---|---|
| `id` | string | Document id (section 2.2). Immutable. |
| `updatedAt` | string | Origin timestamp (section 2.3) of the current state. |
| `deleted` | boolean | `true` for a tombstone. |

The member names above assume a camelCase naming policy; an application MAY use other names if every
peer uses the same serialization contract. Other members are application data.

A replica that writes a document it received MUST NOT drop members it does not understand; it SHOULD
preserve them (for example with `[JsonExtensionData]`) so that an older client cannot erase fields added
by a newer one (I17). Applications SHOULD encode decimal values and 64-bit integers as strings when
non-.NET peers participate.

### 2.2 Identifiers

Document ids and operation ids are strings of 1–256 UTF-16 code units, with no control characters and
no unpaired surrogates. They are compared ordinally (by UTF-16 code unit). Non-ASCII ids are valid.
Operation ids MUST be globally unique; replicas SHOULD use 128-bit random or time-ordered UUIDs.

### 2.3 Origin timestamps

An origin timestamp is a Hybrid Logical Clock value encoded as
`{wallTime:D15}:{counter:D6}:{node}`, where `wallTime` is Unix milliseconds (0–999,999,999,999,999),
`counter` is 0–999,999 and `node` is empty or 1–64 characters from `[A-Za-z0-9._~-]`. Encoders MUST emit
exactly this form; decoders MUST reject anything else. Ordinal comparison of encodings equals timestamp
order.

The authoring replica stamps `updatedAt`. The authority MUST NOT change it. It is metadata for policies
such as last-write-wins, not a version or a cursor.

### 2.4 Versions

Each committed state of a document has a **version**: a positive 64-bit integer. Versions of one document
strictly increase. Versions are encoded as JSON strings of ASCII digits without sign or leading zeros
(`"9007199254740993"`). Decoders MUST reject numbers, signs, leading zeros and values above 2^63−1.

### 2.5 Checkpoints

A checkpoint is an opaque JSON string issued by the authority, or `null` for the start of the feed.
Replicas MUST store and return it verbatim and MUST NOT parse or construct it.

## 3. Messages

### 3.1 Pull request

```json
{ "checkpoint": null, "limit": 100 }
```

| Member | Required | Meaning |
|---|---|---|
| `checkpoint` | yes | The replica's stored checkpoint, or `null`. |
| `limit` | yes | Maximum number of changes to return, ≥ 1. The authority MAY return fewer. |

### 3.2 Pull response

```json
{
  "changes": [ { "document": { ... }, "version": "42" } ],
  "checkpoint": "…",
  "hasMore": false
}
```

- `changes` contains at most `limit` entries and at most one entry per document id: the document's state
  at the page's position, with its version. Tombstones are included.
- `checkpoint` is the position after the page.
- `hasMore` is `true` when further changes are immediately available. If `hasMore` is `true`, the
  checkpoint MUST differ from the request's checkpoint.

### 3.3 Push request

```json
{
  "operations": [
    { "operationId": "…", "documentId": "n1", "baseVersion": null, "document": { ... } }
  ]
}
```

| Member | Required | Meaning |
|---|---|---|
| `operationId` | yes | Id of this logical write (section 5). |
| `documentId` | yes | Equal to `document.id`. |
| `baseVersion` | yes, may be `null` | The version the write was based on; `null` if the replica believes the document is new. |
| `document` | yes | The complete new state (or tombstone). |

A request MUST contain at most one operation per document id. The operations are **independent**: there
is no batch atomicity, and the authority MAY accept some and not others.

### 3.4 Push response

```json
{ "outcomes": [ { "operationId": "…", "kind": "accepted", "version": "43", "document": { ... } } ] }
```

| Member | Present when | Meaning |
|---|---|---|
| `operationId` | always | The operation this outcome answers. |
| `kind` | always | `accepted`, `conflict`, `rejected` or `retry-later`. Decoders MUST reject other values and numbers. |
| `version` | `accepted`, `conflict` | The version after acceptance, or the current version on conflict. |
| `document` | `accepted`, `conflict` | The authoritative state after acceptance, or the current state on conflict. |
| `errorCode` | `rejected`, `retry-later` | Machine-readable reason (section 7). |
| `message` | optional | Human-readable detail. Not localized. |
| `duplicate` | optional, default `false` | `true` when the authority is replaying a stored outcome. |

## 4. Authority rules (push)

For each operation, in request order, the authority MUST:

1. Reject with `invalid` an operation whose ids are invalid, whose `documentId` differs from
   `document.id`, whose `baseVersion` is not `null` and < 1, or whose document already has an operation in
   the same request.
2. If a receipt exists for `operationId`: if the stored request fingerprint (document id, base version and
   canonical document) is equal, return the stored outcome with `duplicate: true` and change nothing;
   otherwise reject with `operation-id-reused` and change nothing.
3. Reject with `clock-skew` if `document.updatedAt` is more than the configured skew ahead of authority
   time.
4. Apply application validation and authorization; reject with their error code if refused.
5. **Conditional write.** If the document exists and `baseVersion` differs from its current version
   (including `null` against an existing document), return `conflict` with the current state and version.
   Otherwise commit the document with a new version.
6. Store a receipt with the outcome of steps 3–5 in the same transaction as any write (I04). Rejections
   in steps 1–2 are not stored.

Steps 5 and 6 MUST be atomic with respect to concurrent operations on the same document (I05).

The current reference authority also accepts a non-null `baseVersion` for a document it does not have.
This is under review (it can silently recreate a document after an authority restore) and is not part of
the conformance suite.

Receipts MUST be retained at least as long as a replica may resend the operation. The reference
authority retains them for its lifetime; bounded retention is Phase 8.

## 5. Replica rules (push)

- A replica MUST persist an operation (id, base version, exact payload) before sending it, and MUST resend
  exactly the same operation until it receives a final outcome (`accepted`, `conflict`, `rejected`).
- A transport failure, cancellation, timeout, `retry-later` outcome or missing outcome means the result is
  unknown; the operation MUST be kept and resent later with the same id.
- A replica MUST refuse (and apply nothing from) a response that contains an outcome for an operation it
  did not send, two outcomes for one operation, an unknown `kind`, or an `accepted`/`conflict` outcome
  without a document and version for the right document id.
- On `accepted`, the replica adopts the returned version as its base. Its local state becomes clean only
  if no later local edit exists; a later edit stays pending on the new base (I02).
- On `conflict`, the replica resolves with its policy using the returned state and version as the new base.
- On `rejected`, the replica parks the record and MUST NOT resend it until a new local edit exists (I19).
- Unsent local edits of one document coalesce into one operation. Once persisted, an operation is
  immutable.

## 6. Feed rules (pull)

- Every checkpoint MUST denote a committed, gap-free prefix of the feed: no change that commits later may
  appear at or before an already-issued checkpoint (I06).
- A replica MUST apply a page's changes and store its checkpoint atomically (I03), MUST refuse a page with
  duplicate document ids or more than `limit` changes, and MUST refuse a page with `hasMore: true` that
  does not advance the checkpoint.
- A replica MUST NOT replace a state with an equal or lower version (I09).
- A replica with unconfirmed local changes to a document keeps its local state and base, and remembers the
  newer server state, which it adopts if its own change later settles on an older version.
- A checkpoint issued by a different authority history (epoch) MUST be refused with a reset requirement.
  The reset procedure (resnapshot preserving pending edits) is not yet specified (Phase 8/9).

## 7. Error codes

| Code | Where | Meaning | Replica action |
|---|---|---|---|
| `invalid` | outcome | Malformed operation. | Park; fix the application. |
| `operation-id-reused` | outcome | Same id, different request. | Park; indicates a replica bug. |
| `clock-skew` | outcome | Origin timestamp too far in the future. | Park until a new edit with a correct clock. |
| `forbidden` | outcome | Not authorized for this write. | Park. |
| `unavailable` | outcome (`retry-later`) | Temporarily unable to decide. | Resend later. |
| `reset-required` | request error | Checkpoint unusable. | Reset flow (not yet specified). |
| `upgrade-required` | request error | Unsupported protocol or schema version. | Stop syncing; upgrade. |
| `payload-too-large` | request error | Request over limits. | Use smaller batches. |
| `rate-limited` | request error | Too many requests. | Wait (`Retry-After`). |
| `unauthorized` | request error | Missing or expired credentials. | Renew credentials. |

## 8. HTTP binding (planned, not implemented)

- `POST {base}/collections/{collection}/pull` with a pull request body; `POST {base}/collections/{collection}/push`
  with a push request body; `application/json; charset=utf-8`.
- Headers `BlazorSync-Protocol: 1` and `BlazorSync-Schema: {application schema id}` on every request.
- Request errors use RFC 9457 `application/problem+json` with a `code` member from section 7.
- Limits (maximum operations per push, maximum page size, maximum body size) are advertised by the
  authority and enforced with `payload-too-large`.
- Scope and principal are taken from the authenticated request, never from the body (ADR-010).

## 9. Versioning

This is protocol version 1. A change that alters the meaning of an existing member or adds a required
member requires a new version. Adding optional response members is compatible; receivers MUST ignore
unknown envelope members.
